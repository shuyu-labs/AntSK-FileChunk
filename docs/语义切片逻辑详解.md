# AntSK-FileChunk 语义切片逻辑详解

## 概述

AntSK-FileChunk 当前的切片实现，目标不是按固定长度机械截断文本，而是在满足长度约束的前提下，尽量保留语义完整性、文档结构和混排顺序。

当前主流程已经与早期版本不同，重点变化有三点：

1. 文件类输入不再先把段落、表格、图片分别拼接后再切，而是优先根据 markdown 内容恢复原始混排顺序。
2. 主切片路径不再依赖“先全局找语义边界，再批量切分”的模式，而是按元素顺序逐个累计，并结合长度与语义连贯性决定是否切开。
3. 切片优化后，如果 chunk 内容被合并、拆分或边界移动，质量评估会按当前内容重算连贯性，不再盲目信任旧的语义得分。

## 核心组件

```text
EnhancedSemanticChunker / SemanticChunker
├── UnifiedDocumentParser   文档解析与 markdown 生成
├── SemanticAnalyzer        向量计算、相似度与缓存
├── ChunkOptimizer          合并/拆分/边界修正/后处理
└── QualityEvaluator        连贯性、完整性、边界质量评估
```

## 第一阶段：文档解析与保序组装

### 1.1 统一文档结构

解析器输出统一的 `DocumentContent`：

```python
@dataclass
class DocumentContent:
    paragraphs: List[Dict]
    tables: List[Dict]
    images: List[Dict]
    metadata: Dict
    structure: Dict
    markdown_content: str
    file_info: Dict
```

这一步的关键不是只拿到文本，而是尽量保留结构化信息，尤其是：

1. 标题与普通段落的类型信息
2. 表格的 markdown 表示
3. 图片的 URL 与文件名
4. 完整 markdown 内容，用于恢复混排顺序

### 1.2 混排顺序恢复

文件类输入的核心预处理逻辑在 `_process_document_content_unified`。当前实现会先尝试根据 `markdown_content` 恢复原始内容顺序，而不是简单遍历 `paragraphs`、`tables`、`images` 三个列表。

恢复逻辑如下：

1. 按空行拆分 markdown block。
2. 表格 block 通过 `_is_markdown_table_block` 识别后映射回表格对象。
3. 形如 `![alt](url)` 的单行图片会映射回图片对象。
4. 其他文本 block 会还原成段落或标题，并与解析结果按内容匹配。
5. 如果 markdown 不可用或匹配失败，则退回到旧的列表顺序。

这样做的直接收益是：

1. “段落 -> 表格 -> 段落 -> 图片” 这类混排文档会按原顺序参与切片。
2. 表格和图片不会被统一挪到文档尾部，减少错误的语义断裂。

### 1.3 元素标准化

统一处理后的 `processed_content` 结构如下：

```python
processed_content = {
    "texts": [],
    "elements": [],
    "element_types": [],
    "markdown_content": document_content.markdown_content,
}
```

不同内容类型的处理方式：

1. 段落：清理空白与特殊字符，长度过短时过滤。
2. 表格：优先使用 markdown 表格文本；没有 markdown 时退回到文本化描述。
3. 图片：在顺序上保留，但用于嵌入计算时放入占位符，如 `[IMAGE_PLACEHOLDER_0]`，最终内容合并时再恢复为 markdown 图片链接。

## 第二阶段：语义分析

### 2.1 向量计算

语义分析由 `SemanticAnalyzer.compute_embeddings` 负责，主要特性：

1. 默认模型为 `all-MiniLM-L6-v2`。
2. 模型按名称缓存，避免重复加载。
3. 文本 embedding 使用 LRU 风格缓存，减少重复计算。
4. 对中文默认截断到 512 字符，对英文默认截断到 256 字符。
5. 图片占位符会被预处理成统一文本，避免无意义的图片 URL 直接参与嵌入。

### 2.2 当前主流程如何使用 embedding

当前主切片路径并不以“全局语义边界列表”作为主要驱动，而是把 embedding 用于逐步判断“新元素加入当前 chunk 后是否仍然连贯”。

换句话说，embedding 现在更像是局部决策信号，而不是一次性全局分段结果。

## 第三阶段：统一顺序切片

### 3.1 主切片入口

当前文件和文本两条主路径最终都会进入：

```python
def _semantic_chunking_unified(self, processed_content, embeddings, document_content) -> List[TextChunk]:
```

这段逻辑是当前实现的核心。它按 `processed_content["elements"]` 的顺序逐个处理元素，而不是先生成边界列表再统一切片。

### 3.2 累计式切片流程

算法状态：

```python
current_chunk_indices = []
current_chunk_elements = []
current_chunk_length = 0
```

对每个元素执行以下步骤：

1. 计算新元素长度。
2. 调用 `_should_start_new_chunk_unified(...)` 判断是否需要切开。
3. 如果需要切开，先把当前累计内容创建成一个 chunk。
4. 根据 `overlap_ratio` 保留末尾若干元素作为重叠内容。
5. 把当前元素加入新的累计状态。

### 3.3 边界决策

统一切片的边界判断分两层：

#### 第一层：结构优先

```python
def _should_start_new_chunk_unified(...):
```

如果满足以下条件，会优先在标题前切开：

1. `preserve_structure=True`
2. 新元素是段落类元素
3. 其 `original_data.type` 为 `heading` 或 `title`
4. 当前 chunk 长度已经达到 `min_chunk_size`

也就是说，标题既是内容，也是结构边界信号。

#### 第二层：长度与语义连贯性

非结构性切分会进入：

```python
def _should_start_new_chunk(self, current_indices, current_length, new_para_length, embeddings, new_para_index) -> bool:
```

当前真实决策顺序如下：

1. 如果加入新元素后超过 `max_chunk_size`，立即切开。
2. 否则计算新元素与当前 chunk 已有元素的平均语义相似度。
3. 只有当语义相似度低于 `semantic_threshold`，且当前 chunk 已达到 `target_chunk_size` 时，才切开。

这意味着：

1. 语义突变本身不会无限制触发切分。
2. 当前 chunk 太短时，系统会倾向于继续累计，避免过碎切片。

### 3.4 连贯性计算

`_calculate_semantic_coherence(...)` 的实现是：

1. 取新元素的 embedding。
2. 与当前 chunk 中所有已有元素的 embedding 逐一计算余弦相似度。
3. 返回这些相似度的平均值。

公式可以概括为：

```text
coherence = mean(sim(new_embedding, existing_embedding_i))
```

### 3.5 重叠策略

统一切片使用元素级重叠：

```python
def _calculate_unified_overlap(self, indices, elements):
```

规则：

1. `overlap_count = max(1, int(len(elements) * overlap_ratio))`
2. 不能超过 `len(elements) - 1`
3. 取末尾 `overlap_count` 个元素作为下一个 chunk 的起始重叠内容

这比旧版按字符或段落粗略重叠更接近实际文档结构。

### 3.6 chunk 创建

每个统一 chunk 由 `_create_unified_chunk(...)` 创建，包含：

1. `content`：通过 `_merge_chunk_content(...)` 合并段落、表格和图片
2. `semantic_score`：对 chunk 内部元素两两相似度取平均
3. `token_count`：按语言估算
4. `chunk_type`：`text_content`、`table_content`、`image_content`、`mixed_content` 之一
5. `metadata`：元素列表、元素数量、文件来源、是否含表格/图片等

## 第四阶段：切片优化

优化入口：

```python
def optimize_chunks(self, chunks: List) -> List:
```

顺序固定为：

1. 合并过小切片
2. 分割过大切片
3. 优化切片边界
4. 后处理

### 4.1 合并过小切片

触发条件：chunk 长度小于 `min_chunk_size`。

策略：

1. 尝试与相邻切片合并。
2. 合并后长度不能超过 `max_chunk_size`。
3. 合并后的 chunk 会标记 `requires_score_refresh=True`，提示后续评估重新计算连贯性。

### 4.2 分割过大切片

触发条件：chunk 长度大于 `max_chunk_size`。

策略：

1. 优先按句子边界拆分。
2. 无法按句子拆分时，退回到按字符强制切分。
3. 子 chunk 会带上 `requires_score_refresh=True`，表示旧分数不再可信。

### 4.3 边界修正

当前的边界优化已经不是空实现，而是一个最小可用的句边界修正器。

核心逻辑：

1. 如果前一个 chunk 末尾已经是句子边界，不处理。
2. 否则，在后一个 chunk 开头查找第一个句子结束符。
3. 如果能找到，就尝试把这一小段前缀移动到前一个 chunk 尾部。
4. 只有同时满足以下条件才移动：
   - 前一个 chunk 拼接后不超过 `max_chunk_size`
   - 后一个 chunk 移除前缀后仍不小于 `min_chunk_size`
   - 移动前缀和剩余内容都非空

这一步主要用于修正类似下面的情况：

```text
chunk1: This sentence is cut
chunk2: off here. Next sentence remains.
```

优化后会变成：

```text
chunk1: This sentence is cut off here.
chunk2: Next sentence remains.
```

边界调整后的两个 chunk 都会打上以下元数据：

1. `boundary_adjusted=True`
2. `boundary_adjustment=...`
3. `requires_score_refresh=True`

### 4.4 后处理

`_post_process_chunks(...)` 负责收尾：

1. 重新生成连续的 `start_pos` / `end_pos`
2. 清理多余空行和首尾空白
3. 重新估算 token 数量
4. 写入 `chunk_id`

## 第五阶段：质量评估

评估入口：

```python
def evaluate_chunks(self, chunks: List) -> Dict:
```

当前评估维度：

1. `coherence` 连贯性
2. `completeness` 完整性
3. `length_balance` 长度平衡性
4. `semantic_density` 语义密度
5. `boundary_quality` 边界质量

### 5.1 连贯性评估

当前实现的重要变化是：

1. 普通 chunk 可以直接使用已有 `semantic_score`
2. 如果 `metadata.requires_score_refresh=True`，则强制按当前内容重算

重算逻辑：

1. 先把 chunk 内容按句子拆分
2. 对句子重新计算 embedding
3. 计算相邻句子的平均相似度

这样可以避免以下失真：

1. 合并后仍沿用合并前平均分
2. 分裂后仍沿用父 chunk 分数
3. 边界移动后仍保留旧分数

### 5.2 完整性评估

完整性使用启发式规则：

1. 是否以句号、问号、叹号、分号等结束
2. 开头是否像不完整残句
3. 末尾是否有 `(续)`、`(未完)`、`...`、`……` 等截断信号
4. 对对话内省略号与“详见”类引用做较温和处理

### 5.3 边界质量评估

边界质量使用两类信号：

1. 上一个 chunk 尾部和下一个 chunk 头部的语义相似度
2. 是否落在自然句边界、章节起始等更合理的位置

### 5.4 综合评分

综合分数使用固定权重：

```python
weights = {
    'avg_coherence': 0.3,
    'avg_completeness': 0.25,
    'length_balance': 0.15,
    'avg_semantic_density': 0.15,
    'boundary_quality': 0.15,
}
```

## 当前默认配置

当前 `ChunkConfig` 默认值如下：

```python
@dataclass
class ChunkConfig:
    min_chunk_size: int = 500
    max_chunk_size: int = 3000
    target_chunk_size: int = 1800
    overlap_ratio: float = 0.1
    semantic_threshold: float = 0.6
    paragraph_merge_threshold: float = 0.8
    language: str = "zh"
    preserve_structure: bool = True
    handle_special_content: bool = True
```

FastAPI 对外暴露的默认参数也已经改为直接复用 `ChunkConfig()`，避免 API 默认值和内部默认值不一致。

### 参数调优建议

| 参数 | 当前作用 | 调优建议 |
|------|------|----------|
| `min_chunk_size` | 控制过碎切片 | 下游检索不喜欢短片段时适当提高 |
| `max_chunk_size` | 控制硬上限 | 下游上下文窗口更大时可提高 |
| `target_chunk_size` | 控制语义切分的触发前提 | 值越大，系统越倾向于延迟切分 |
| `semantic_threshold` | 控制语义突变敏感度 | 值越高越容易切开，值越低越倾向合并 |
| `overlap_ratio` | 控制上下文重复 | 提高可增强召回，但也会增加冗余 |
| `preserve_structure` | 控制标题是否优先断开 | 面向文档问答时通常建议开启 |

## 当前实现的特点

### 1. 保序优先

当前实现优先保持原始 markdown 混排顺序，这一点对含表格、图片、标题的文档非常重要。

### 2. 顺序累计切片

切片是一个逐元素的在线决策过程，而不是先全局聚类再一次性切分。这样更容易同时兼顾长度约束和结构边界。

### 3. 后处理结果可回评

优化器对 chunk 做过内容级修改后，会明确告诉评估器“旧分数失效，需要重算”，因此质量分数更接近最终输出，而不是接近中间态。

### 4. 保守但可控

当前实现仍然偏工程化和保守：

1. 结构边界优先级高于部分语义信号
2. 只有在达到目标长度后才更积极地按语义切分
3. 边界修正目前只做最小可用的句边界回补

这让行为更可预测，也更便于继续迭代。

## 使用示例

### 基本使用

```python
# 初始化配置
config = ChunkConfig(
    target_chunk_size=1000,
    semantic_threshold=0.75,
    language="zh"
)

# 创建切片器
chunker = SemanticChunker(config=config)

# 处理文件
chunks = chunker.process_file("document.txt")

# 处理纯文本
chunks = chunker.process_text("长篇文本内容...")

# 获取统计信息
stats = chunker.get_chunking_statistics(chunks)

# 保存结果
chunker.save_chunks(chunks, "output.json")
```

### 高级配置

```python
# 严格语义要求的配置
strict_config = ChunkConfig(

fast_config = ChunkConfig(
    target_chunk_size=1500,     # 更大的切片
    semantic_threshold=0.6,     # 更宽松的语义要求
    overlap_ratio=0.05,         # 更少重叠
    language="zh"
)
```

## 总结

AntSK-FileChunk的语义切片系统通过集成先进的语义分析技术和智能的切片算法，实现了高质量的文本分割功能。系统不仅考虑文本的物理长度限制，更重要的是保持语义的完整性和连贯性，为下游的文本处理任务（如RAG检索、文档分析等）提供了高质量的文本片段。

该系统的核心优势在于：
1. **智能边界检测**: 基于语义相似度的边界识别
2. **多层优化**: 从初步切片到最终优化的多阶段处理
3. **质量保证**: 完善的质量评估和统计分析
4. **灵活配置**: 丰富的配置参数适应不同场景需求
5. **高性能**: 优化的算法设计和计算流程

这使得AntSK-FileChunk成为一个功能强大、性能优异的智能文本切片解决方案。
